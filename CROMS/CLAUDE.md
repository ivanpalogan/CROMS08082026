CROMS — Civil Registry Operations Management System

Full name: Civil Registry Operations Management System Client: LGU Peñablanca, Cagayan — Local Civil Registry Office (LCRO) Type: Desktop application (Windows Forms / C# .NET Framework 4.8) Purpose: A day-to-day operations system for the LCRO — not just a digitization tool, but the everyday workbench that staff use to register events, serve clients, issue certifications, track petitions, and submit reports to PSA.



What it does (in one paragraph)

CROMS replaces the paper-and-spreadsheet workflow of the LCRO with a single integrated desktop app. Clients get a queue number at the front desk, the receiving officer logs the transaction, the registrar processes the record (birth, marriage, death, or certification request), the cashier assesses fees against the Peñablanca Revenue Code, and the releasing officer captures the claimant's signature — all tied to one transaction ID with a full audit trail. In parallel, the office digitizes decades of old registry books through the OCR module, and generates PSA monthly submission reports automatically from the same database.



The 15 modules

🟦 Client Services (front-desk workflow)

Module	What it does

Dashboard	Live KPIs — queue length, today's registrations, collections, pending releases.

Queue Management	Issues numbered tickets (BIRTH-###, CERT-###, etc.), calls next client, tracks wait time.

Transactions	Master ledger of every client interaction — one TXN ID follows the client from queue to release.

Certificate Request	Intake for CTC (Certified True Copy) of Birth/Marriage/Death and Negative Certifications.

Release \& Claim	Captures claimant signature (or authorized representative + ID) on release; closes the transaction.

🟩 Record Management (the registry itself)

Module	What it does

Birth Registration	Municipal Form 102 — full data entry for live-birth registration.

Marriage Registration	Municipal Form 97 — marriage certificate registration.

Death Registration	Municipal Form 103 — death certificate + burial permit.

Registry Books	Digital equivalent of the physical registry books, organized by year/volume/page.

Petitions (RA 9048 / 10172)	Tracks correction-of-entry and change-of-first-name petitions through their legal stages (Filed → Posted → Decision → PSA endorsement).

Record Search	Cross-record search with fuzzy / SOUNDEX matching (so "Dela Cruz" finds "dela cruz" and "de la Cruz").

🟨 Document Workflow

Module	What it does

Incoming / Outgoing	Document routing log — what came in, where it went, who signed for it.

OCR Digitization	Scans old registry pages, runs OCR, shows confidence levels, lets staff verify and commit to the database. This is how the backlog gets digitized without replacing the daily workflow.

🟧 Operations

Module	What it does

Fees \& Payments	Auto-assesses fees per the Peñablanca Revenue Code, adds any additional charge, records payment method / reference / status / tendered+change, and reconciles Official Receipt numbers with the Treasurer.

Reports \& PSA	Generates the PSA monthly submission report (BReN, MReN, DReN counts) and internal management reports.

🟥 Administration

Module	What it does

Users \& Audit Trail	User accounts, role-based access (Registrar / Staff / Cashier / Releasing), and a tamper-evident audit log of every create/update/delete.

Why it's designed this way

Realistic, not ambitious. It solves what LCRO staff actually do every day — queue, register, assess, collect, release, report — instead of chasing AI features they don't need.

Deployable. WinForms + .NET 4.8 + MySQL runs on any office PC the LGU already owns. No cloud dependency, no subscription.

Survives past digitization. Even after every old book is scanned, the app is still the daily operations system — that's the whole point.

PSA-compliant. Uses the official Municipal Form numbers (102/97/103) and produces the monthly report PSA expects.

Auditable. Every transaction has one ID, one owner, one signature trail — important for a government office.

### 2026-07-14 — Domain research: PSA ↔ LCRO process (informs the Reports module)
- CORRECTION to the top-of-file pitch wording: **BReN / MReN / DReN are Birth/Marriage/Death REFERENCE NUMBERS printed on the PSA security paper (SECPA)** of an authenticated certificate (with QR + serial) — they are NOT the monthly report's count fields. The monthly thing the LCRO sends PSA is a **transmittal/endorsement of the registered vital events** for the period.
- Registration chain: informant → LCRO registers the event + keeps the registry book → monthly transmittal to PSA (via Provincial Statistical Office → OCRG) → PSA later issues the nationwide authenticated copy on SECPA. The "Certificate of Live Birth" (MF102) and a "PSA birth certificate" are the SAME record — original vs authenticated copy. A CROMS `births` row = the COLB; Certificate Request just issues a CTC of it.
- Three registrable events / forms, each accomplished in quadruplicate: Birth = MF102 (COLB), Marriage = MF97 (COM), Death = MF103 (COD).
- Reglementary (on-time) period: RA 3753 — birth must be registered within 30 days; past that = late/delayed registration (extra affidavits). Schema already has `births.is_delayed`, so the monthly report SHOULD split timely vs delayed.
- Implication for Reports & PSA module design: a monthly Report of Registered Vital Events per event type = counts (births/marriages/deaths registered in the chosen month) + timely-vs-delayed split (from `is_delayed`/registration date) + a detail roster (registry no, name, date of event, date registered, status) + collections summary (SUM `payments.net_amount`) + CSV/print export. All buildable from existing tables.

### 2026-09-08 — Two registry-integrity defects fixed: the PSA delayed count, and the duplicable registry number
Found by auditing what the system still needs to be defensible as a government records system,
not by a bug report. Both were live and both are the kind a panel finds by asking an obvious
question ("how do you know which births were late?", "what if two people save at once?").

**DEFECT 1 — THE MONTHLY PSA SUBMISSION WAS STATUTORILY WRONG.** `births.is_delayed` was a
checkbox the registrar had to remember to tick, and nobody ever did: it is 0 on all 18 rows
while DATEDIFF says 16 were registered more than 30 days after the birth. `ReportsPsaForm`
reads that flag for the RA 3753 timely-vs-delayed split, so the report PSA receives was
claiming every registration was timely. The Dashboard had already stopped trusting the flag
(2026-09-07 entry computes from DATEDIFF deliberately) — the report never got the same fix.

**The obvious repair was wrong, and that is the important part.** Deriving it from `created_at`
would mark the entire OCR backlog delayed: `created_at` is when the ROW was made, which for a
typed-in registration is the registration date but for a scan is the DIGITIZATION date.
Scanning a 2018 certificate in 2026 is not a late registration — that birth was registered in
2018, on paper. The database simply had nowhere to record WHEN an event was registered.

So migration 27 adds `births.date_registered`, written only when a registration actually
happens (today for a real registration, NULL for a Draft, and the record keeps its own date on
edit so correcting a typo in a 2019 record cannot re-date it to today and turn it delayed). The
OCR commit path deliberately does not set it — checked, it never touched `is_delayed` either —
so a digitized record stays NULL. **Existing rows are left NULL on purpose**: we cannot tell
retroactively which were true registrations and which were migrated or digitized, and guessing
either way would put a fabricated statutory claim in a government return. The PSA report now
counts the split ONLY over rows with a known registration date and states the remainder
separately ("N not counted — no registration date on record"), and the roster's Registration
column reads "Not recorded" rather than the false "Timely" it used to print.

`RecomputeDelayed` sets the box from the dates on every date-of-birth change, and the label now
shows the arithmetic ("birth was 3,010 days ago, past the 30-day period") so a registrar who
disagrees can see what was counted before overriding. It stays overridable — whether a
registration is delayed is their determination, they collect the affidavits. Loading a record
shows the STORED determination, never a recomputation.

**DEFECT 2 — THE REGISTRY NUMBER COULD BE DUPLICATED.** `registry_no` is the record's legal key
and carried only a plain index. All three forms generate it with MAX+1, read in one statement
and written in another, so two registrars saving in the same moment both read the same maximum
and both write the same number — the "tiny race window" flagged back on 2026-07-14, with
nothing in the schema to stop it landing. Migration 27 makes it UNIQUE on births/marriages/deaths.

**A constraint alone would have made this worse**, so the retry is half the fix: the loser of the
race now gets error 1062 instead of writing a duplicate, and a save that does not handle that has
merely traded silent corruption for a crash in front of a client. New `Data/RegistryNumber.cs`
holds the year-scoped MAX+1 (it was triplicated, so a fix to one left the other two wrong) and
`WasTaken`, which matches on the INDEX NAME and not merely on 1062 — a duplicate on any other
unique column must not be retried into an endless loop. All three save paths, plus Birth's update
path (promoting a draft assigns a number too), now take the next number and retry.

**VERIFIED AGAINST THE LIVE DATABASE AND THE BUILT BINARY, not by compiling.**
  - Pre-checked before applying: no duplicates exist, and every blank `registry_no` is NULL, not
    `''` — which matters, because UNIQUE permits many NULLs but treats `''` as a value, so two
    empty strings WOULD collide. The migration normalises any `''` to NULL first for fresh
    installs, and refuses with a readable message (naming the count and the query to find them)
    rather than letting ALTER abort mid-way if a database ever does hold duplicates.
  - Constraint proven both ways: a duplicate number is rejected (1062), two NULL drafts are still
    accepted. `RegistryNumber.WasTaken` driven against a REAL MySqlException off the live server —

    (the infinite-loop guard).
  - The race reproduced end to end: two "registrars" both computed 2026-B-0003, A saved it, B was

    second 2026-B-0003.
  - `RecomputeDelayed` driven on the shipped exe across the boundary: 30 days -> not delayed,
    31 days -> delayed. Loading id 22 (DOB 2018, stored flag 0) keeps the box unticked while the
    label states the disagreement — so the data problem the analytics module found on 2026-09-07
